M-C2-001 | Continual Harness (definition) | LLM Refiner edits harness H from the most recent trajectory window during a single continuous episode; generalizes reset-based prompt optimization (which rewrites only p from complete-episode resets, refs [1,14]) to rewriting the full state from the trajectory so far; agent never resets | §3 (opening, before 3.2)
M-C2-002 | Observation state | s_t = (o_t, m_t) written as agent's observation at step t | §3
M-C2-003 | Inner loop | Standard agent step: model M wrapped by current harness H_t produces action a_t from s_t and trajectory so far | §3
M-C2-004 | Outer loop | Harness refinement: every F steps after a warm-up of W steps, a Refiner reads the recent trajectory window for failure signatures and emits per-component edits delta = (delta p, delta G, delta K, delta M); updated harness H_{t+1} = H_t XOR delta enters agent's context on next step (Figure 2a) | §3
M-C2-005 | Harness edit application | p replaced by delta p; G, K, M receive CRUD-style operations (create, read, update, delete) | §3
M-C2-006 | Agent/Refiner model sharing | Agent and Refiner roles share the same model M, ablated across Gemini 3.1 Pro, Flash, and Flash-Lite (§4); differ only in when invoked and on what trajectory context; both issue edits through the same meta-tool API (§2) | §3
M-C2-007 | Refinement window input | Refiner reads tau_{t-F:t} (last F-step trajectory window) | §3.2
M-C2-008 | Failure signatures | Identified over window: navigation loops, tool-call failures, stalled objectives, missed exploration opportunities | §3.2
M-C2-009 | Pass 1 — prompt | Rewrites prompt p conditioned on identified failures and trajectory window | §3.2
M-C2-010 | Pass 2 — sub-agents | Creates sub-agent entries for repeated multi-step patterns, edits existing entries to address detected failures, deletes entries not invoked productively | §3.2
M-C2-011 | Pass 3 — skills/code | Codifies skills from successful sequences and repairs executable code that raised exceptions | §3.2
M-C2-012 | Pass 4 — memory | Adds memory entries to fill gaps, updates stale entries, demotes importance for areas the agent has moved past | §3.2
M-C2-013 | Monotonic refinement accumulation | Refinement information accumulates monotonically: failure signatures observed earlier remain available to all subsequent passes, so refinement quality compounds with episode length; reset-based methods restart accumulation after each update | §3.2
M-C2-014 | Late-failure targeting | Continual Harness can target failures appearing only deep in an episode (late-game battles, multi-step puzzles, dialogue chains), which reset-based approaches cannot reach by construction | §3.2
M-C2-015 | Co-learning loop | After warm-up stages (Appendix D), each online iteration runs pi_theta_k inside live-refining harness H_t for K = 256 steps | §3.3
M-C2-016 | Process reward model | Pairwise PRM R(s_t, a_t, tau) in [0,1] scores each transition over a sliding window of recent transitions (component weights in Appendix D) | §3.3
M-C2-017 | Relabel + SFT update | Low-reward windows relabeled by a frontier teacher; soft SFT update on the relabeled shard produces theta_{k+1} | §3.3
M-C2-018 | Reset-free state carry | Saved emulator state at end of iteration k is loaded as start of iteration k+1; model's in-game position accumulates across training rather than restarting | §3.3
M-C2-019 | Co-learning update split | theta updated across iterations (via SFT on relabeled trajectories); H_t updated within each iteration (via the Refiner); trajectory distribution D_theta depends on theta through the harness | §3.3
